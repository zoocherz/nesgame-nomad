# Реальная рабочая переписка с Claude Code: диагностика и исправление NES-игры

Ниже — дословная выдержка из реальной сессии Claude Code по личному проекту NES-игры. Это не реконструкция и не пересказ. Из исходной выгрузки удалены только локальные пути, ссылки на временные артефакты, служебные строки интерфейса и листинги кода; они обозначены `[скрыто]`. Технические выводы, вопросы, варианты решений и ответы пользователя оставлены без переформулирования.

## Кто участвует

- **Пользователь** — владелец проекта: ставит направление, выбирает между вариантами и принимает продуктовые риски.
- **Оркестратор Claude Code** — разбирает проблему, формулирует варианты, делегирует работу и проверяет результат.
- **nes-architect**, **game-designer**, **gameplay-dev**, **qa-tester** — субагенты, которым оркестратор ставит отдельные задачи.

## Контекст фрагментов

Ниже показаны две последовательные части работы. В первой владелец проекта
фиксирует результат предыдущего исправления, описывает оставшуюся проблему на
двух игровых уровнях и формулирует задания по анализу. Во второй оркестратор
после диагностики отдельного риска передаёт его субагентам, возвращает варианты
на решение владельцу и организует независимую приёмку.

Этот раздел — редакционная вводная, не часть исходной переписки. Начиная со
следующего заголовка сохранён дословный текст, кроме обозначенных удалений.

### Фрагмент 2. Декомпозиция отдельного риска, решение и приёмка

**Оркестратор Claude Code**

> Провёл решающий тест — построчно сравнил рисунок тумана на 60 рядах карты 1-2: один раз при обычном первом пролёте, второй раз после рестарта (смерть+возрождение). Совпало 60 из 60 рядов, 0 расхождений. Первый спавн Mosquito в обоих случаях — ровно на мировом ряду 44, кадр в кадр одинаково.
>
> Это значит: рисунок тумана вообще не знает, был рестарт или нет — он полностью детерминирован номером ряда карты, без всякой случайности. А полоса, которую вы видите, — это уже известный и объяснённый G2-дефект (плотность/скачки тумана на отдельных рядах при обычном скане, не связанный с CPU-нагрузкой и не связанный со смертью).
>
> Кстати, попутно нашёл (не про полосу тумана) реальный, но отдельный риск: спавн-проверки Mosquito из последних двух коммитов на кадре спавна группы съедают ~19% бюджета кадра разом — это может давать редкий рывок/пропуск кадра. К полосе тумана отношения не имеет, но чинить стоит отдельно.

**Пользователь**

> Хорошо, давай подключим архитектора к этим задачам

**Оркестратор Claude Code**

> Запускаю архитектора первым этапом — он должен дать точный, реализуемый план (без него gameplay-dev рискует повторить провалы G2/G2' с тем же классом WCET-ошибок).

**Оркестратор → субагент `nes-architect`**

> Детальный план фикса WCET-риска спавна Mosquito

**Оркестратор Claude Code, после результата архитектора**

> Архитектор закончил и дал важную поправку к моему собственному плану — исходные F1/F2 он сам же отклонил.
>
> Диагноз точнее, чем думали: пик не в «слишком много работы», а в неправильной вложенности циклов — обе функции сканируют пул астероидов по 18-20 раз точечными зондами 8×8, хотя это решается одним проходом по 6 астероидам с проверкой пересечения прямоугольников.
>
> Почему F1/F2 отклонены:
>
> - F2 («по одному X-кандидату за кадр») физически ломает лимит «≤8 спрайтов на строке» — запас по стаггеру у формации «Гребёнка» всего 1.2 кадра, задержка на 2+ кадра гарантированно даёт конфликт по спрайтам. Не обсуждается.
> - F1 («18 проб размазать по кадрам») — тот же класс решения, что дважды провалился в terrain.c (G2/G2'): переносит расход с редкого кадра на каждый кадр, ломает бесплатный «пустой» путь.
>
> Предложенный план А: один новый примитив `asteroids_rect_hit()` (прямоугольник вместо 18-20 точек) в `[скрыто]`, два места вызова в `[скрыто]` — без единой новой переменной состояния между кадрами, значит без крайних случаев «смерть посреди проверки». Пик снижается с 19.1% до 4.5% кадра (×4.2), калибровочный (самый частый) путь остаётся бесплатным.
>
> Есть один нюанс, требующий вашего решения: прямоугольник строго покрывает больше площади, чем старые точечные зонды (закрывает «дыры» между ними) — значит формации будут чуть чаще выбираться боковыми, а спавн чуть чаще сдвигаться/отменяться при кучности астероидов. Архитектор явно попросил не коммитить это молча.

**Пользователь**

> Сначала показать game-designer

**Оркестратор Claude Code**

> Запускаю game-designer, чтобы обсудить именно баланс-дельту (§3 из плана архитектора) до того, как код тронут.

**Оркестратор → субагент `game-designer`**

> Оценка баланс-дельты фикса CPU-пика Mosquito

**Оркестратор Claude Code, после результата дизайнера**

> Дизайнер закончил анализ и рекомендует принять точную проверку без сужения зон.
>
> Ключевой аргумент: полоса 32..72 для `top_band_occupied()` — не «с запасом», а математически ровно зона реальной угрозы (посчитано по скорости сближения камня и звена: угроза физически невозможна дальше d=40 px). Сужение вернуло бы тот самый баг, ради которого делались V1/V2/V3.
>
> По ощущению игры: дельта тонет в шуме. TOP-формации: ~48% → ~38% случаев (примерно минус 2 звена сверху за минутный прогон 1-2), при стандартном отклонении ±2.2 — статистически неотличимо от прогона к прогону. «Занавеска сверху» как визитная карточка уровня не пропадает.
>
> Дал qa-tester’у 8 конкретных критериев приёмки (AC1-AC8), включая сам факт снижения CPU-пика с ~19% до ≤5%.

**Пользователь**

> Согласен, план А без сужения
>
> Подождать AC8 на живой сборке

**Оркестратор Claude Code**

> Оба решения приняты — план А без сужения зон, F-2 не трогаем заранее. Передаю реализацию gameplay-dev.

**Оркестратор → субагент `gameplay-dev`**

> Реализация rect-проверки астероидов (WCET-фикс Mosquito)

**Оркестратор Claude Code, после результата реализации**

> gameplay-dev реализовал фикс и сам получил ~5.2% против прежних ~19% на композитном худшем кадре — но полную регрессию (все 69 lua-тестов) не прогонял, только репрезентативный набор. Запускаю qa-tester для независимой полной проверки, как того требует правило проекта.

**Оркестратор → субагент `qa-tester`**

> Полная проверка WCET-фикса Mosquito/астероидов

**Оркестратор Claude Code, после результата QA**

> Тема закрыта. qa-tester лично перепроверил и не поверил отчёту gameplay-dev на слово.
>
> Итог: точечные зонды заменены на точный `asteroids_rect_hit()`, пик снижен с ~19% до 5.19% кадра. Полная регрессия по зонам риска (mosquito_*, asteroids, enemy_bullet_*, level_1_2, oam_*, fog_*) — 0 сбоев.
>
> Одна некритичная оговорка: проверка баланса формаций (AC1) набрала только 57 решений из 200 нужных для статистической значимости (упёрлось в лимит headless-прогона Mesen на один процесс) — качественно всё нормально (ни одна формация не выродилась), но строгого доказательства нет. Не блокер, можно нарастить позже через savestate-цепочку при желании.

## Границы материала

Это личный технический проект. Выдержка демонстрирует реальное взаимодействие владельца проекта с LLM-оркестратором и субагентами, но не является кейсом заказчика и не подтверждает самостоятельную production-разработку AI-агентов, RAG, MCP или корпоративной AI-архитектуры.
